## DB-20260720-01 Claude Code v2.1.215:/verify・/code-review の自動実行が廃止、明示起動方式へ

**要点: Claude Code の品質チェック系スキルが「勝手に走る」前提が崩れた。組織標準が既定挙動に依存していないか点検が必要。**

### 確認された事実

Claude Code v2.1.215 がリリースされた(2026-07-19)。

- Claude が /verify および /code-review スキルを自律的に実行しなくなった。
- 必要な場合は本人が /verify・/code-review で明示的に起動する方式に変更された。

リリースノートに記載された変更点は上記のみ(原文照合済み)。

### なぜ重要か

**「AIが自動で品質チェックしてくれる」前提の運用は、ツールのバージョンアップ1つで崩れることが示された。**

- 検証・レビューを既定挙動に任せた統制は、アップデートで無効化されうる。
- 組織展開時の統制は、既定値ではなくフック・CI 等の強制手段に置く必要がある。

### 自分の業務への示唆

**Claude Code 組織展開の標準・教育資料のうち「自動でチェックが走る」前提の記述を洗い出す材料になる。**

- 利用ガイドに「/verify・/code-review は明示起動する」ことを明記する必要がある。
- レビュー必須の統制は、Claude 側の挙動ではなくフックや CI パイプラインで担保する設計に寄せる根拠になる。

### 推奨アクション

**自組織の Claude Code 利用標準ドラフトから、既定挙動依存の箇所を点検する。**

- 「自動で品質チェックされる」前提の記述を洗い出し、明示起動またはフック強制に書き換える。

## DB-20260720-02 Google「AlphaEvolve」がGA:進化的コード最適化のサービス化と適用条件

**要点: AI によるコード最適化が研究からエンタープライズ向けサービスに移行。「測定可能な評価関数があるか」が適用可否の線引きになる。**

### 確認された事実

Google の AlphaEvolve が Gemini Enterprise Agent Platform 上で一般提供(GA)に到達し、DeepMind の研究プロジェクトが進化的コード最適化サービスになった。

- 評価器(evaluator)は顧客側インフラ(ラップトップ・プライベートクラスタ等)で実行され、スコアリングはローカルで完結する。候補プログラムの生成は AlphaEvolve の API 側で行われる。
- Klarna は ML 学習スループットを2倍にした(Google の発表に基づく顧客事例数値。約3週間で約6,000件の候補プログラムを探索)。
- InfoQ 記事の著者は、顧客事例と実務者のコメントを踏まえ「測定可能で自動化できる評価関数がある問題」でのみ機能すると整理している。

### なぜ重要か

**「AI最適化はどこにでも効く」のではなく、適用条件が明確に示された点が実務上の価値。**

- 評価関数を定義できる対象(性能・コスト等の定量指標がある処理)に適用が限定される。
- 評価器の実行とスコアリングを顧客環境内で完結させる設計は、データ主権を重視する企業向けの導入パターンとして参照できる。

### 自分の業務への示唆

**顧客提案で「AI最適化が刺さる領域」を見極めるチェック基準として使える。**

- 提案前に「この処理には測定可能な評価関数があるか」を問うだけで、PoC 倒れ案件の足切りができる。
- セキュリティ懸念の強い顧客への説明で、「評価はお客様環境内で完結する」型のアーキテクチャを選択肢として提示できる。

### MBA視点での示唆

**AI投資のデューデリ項目に「評価関数の有無」を加えるべきことを示す事例。**

- Klarna の数値は Google の発表(顧客事例)に基づく二次情報で第三者検証はなく、提案書で使う場合は帰属を明示する。

### 推奨アクション

**自社・顧客のワークロードから「測定可能な評価関数を持つ最適化対象」を挙げてみる。**

- 性能・コスト・スループット等の定量指標が既にある処理を候補として3つ書き出す。
- 工数: 30分。
- 完了条件: 適用候補3件と、それぞれの評価指標のメモが1枚できている。

## DB-20260720-03 AWS「CloudFormation Express Mode」:安定化を待たない高速デプロイ

**要点: デプロイ高速化と引き換えに「安定化確認」を省く方式。速度と検証のどちらに倒すかの判断が利用側に移る。**

### 確認された事実

AWS が CloudFormation express mode を導入した。

- リソースの完全な安定化(stabilization)を待たず、create / update / delete の API 呼び出しが成功した時点でスタック操作を完了扱いにすることで、インフラのデプロイ時間を短縮する。
- 完了扱いの時点ではリソースが初期化中・トラフィック処理不可の場合があり、完全稼働が必要な場合は従来の安定化確認付きの既定動作を使うよう案内されている。
- 記事では、express mode でロールバックが既定で無効になる点を懸念する実務者のコメントも紹介されている。

### なぜ重要か

**「完了扱いを早める=安定化の確認を省く」というトレードオフを、利用側が明示的に選ぶ機能である点。**

- 本日の DB-20260720-01 と同じく、「速度のために検証を既定から外す」流れの一例として押さえておく。

### 自分の業務への示唆

**IaC 標準で express mode の適用可否(本番/検証環境の別)を決める論点が増える。**

- 検証環境では高速化、本番では安定化確認を待つ、といった環境別の使い分け基準を標準に書く材料になる。

### 推奨アクション

なし(継続監視)。IaC 標準を改訂するタイミングで環境別の適用基準として検討する。
